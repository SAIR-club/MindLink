# 0002 — 学习单元与循环

状态：**提议，待讨论**（2026-10-26）。对应审查报告 M5、M6。本 ADR 定稿之前不实现控制流。

## 背景

引擎让每个步骤只执行一次（`engine/advance.ts`，完成的步骤按路径记进 `done` 集合），没有循环，也没有条件。`explain` 的说明是"讲清一个概念"，而一次速通往往要覆盖一章十来个知识点；"答错了就重讲""时间不够就缩小范围"现在只能靠 agent 在一步之内即兴发挥，系统看不见，也无法比较。

第一轮审阅补充了两点：

1. 学习单元不能等同于知识点。读论文的单元是研究问题、方法和实验；做项目的单元是里程碑；训练批判性思维的单元是一段论证或一个待解决的矛盾。
2. 引擎不应内置"学会"的定义。自测可以按正确率结束，引导提问可能以产生新问题结束，认知冲突可能以"明确保留未解决"结束，深度探究可能没有简单的通过条件。

## 决定（提议）

### 1. 学习单元

**单元是可以单独设定目标、执行活动、评价结果的学习任务。**

```json
{
  "id": "u3",
  "title": "TCP 三次握手",
  "type": "concept",
  "goal": "能说清为什么需要三次而不是两次",
  "status": "pending"
}
```

- `type` 是自由标签，建议用 `concept`、`milestone`、`question`、`method`、`experiment`、`argument`、`conflict`。引擎不解释它，只用于展示和统计。
- `goal` 是这个单元自己的目标，一句话，可选。
- `status`：`pending`、`active`、`done`、`dropped`。

单元列表存在**运行**里（`StoredRun.units`），不存在项目里：一次学习一份议程。

### 2. 单元从哪里来

由积木产生，不限定是哪一块。活动积木可以声明 `produces: units`，然后在 `workflow_report` 里附上 `units`（一组单元）。`map` 只是其中一种来源；`apply` 的单元可以来自规划里程碑的积木，读论文的单元可以来自拆解论文的积木。

学习者可以随时增删、改顺序、把某个单元标为完成或放弃（REST 和 MCP 各一个入口）。

### 3. 循环

工作流里的一组步骤可以对每个单元重复执行：

```yaml
steps:
  - use: goal
  - use: map            # produces: units
  - id: per-unit
    repeat: units       # 对 pending 的单元依次执行
    steps:
      - use: explain
      - use: recall
        until: "recall.correct >= 2 and verified(recall.correct)"
        max: 2
        otherwise: next # next | stop | ask
  - use: distill
```

- `repeat: units` 只能出现一层，不支持嵌套循环。
- 循环体内的积木说明里可以引用当前单元：`{{unit.title}}`、`{{unit.goal}}`、`{{unit.type}}`。

### 4. 退出条件：通用表达式，引擎不内置"学会"

- `until` 是一个小的条件表达式，**只能读本单元、本次循环内已报告的结果字段**（ADR 0001 的字段，含评价者和是否验证），比如 `recall.correct`、`guide.outcome`。
- 语法只包括：
  - 字段引用；
  - 字面量（整数、字符串、`true` / `false`）；
  - 比较 `== != < <= > >=`；
  - `and` / `or` / `not`；
  - 谓词 `verified(字段)`，表示这个评价字段是否验证过（ADR 0001）。
  
  没有函数调用，不访问别的单元，不访问认知状态。
- 条件不满足就把这一步再做一次，最多 `max` 次（必填，上限 5）。用完次数仍不满足，按 `otherwise` 处理：
  - `next`：进入下一单元，这个单元记为"未达成"；
  - `stop`：结束循环；
  - `ask`：把决定交给学习者或 agent。`workflow_next` 返回"等待决定"，由 `workflow_next` 的参数选择下一步。
- **不写 `until` 就没有自动条件**：每个单元执行一次，由学习者或 agent 决定什么时候结束。保留冲突、深度探究这类没有简单通过条件的活动就这样写。
- 解析时校验表达式：引用的字段必须是循环体内积木声明过的结果字段，类型必须匹配。

### 5. 时间预算

项目可选 `timeBudget`（分钟）。引擎**不自动删减单元**，只在 `workflow_next` 的返回里给出已用时间、剩余单元数和预算，由积木说明和 agent 据此调整（比如"时间不够时，后面的单元只做自测"）。怎么取舍是教学策略，不进引擎。

### 6. 运行时上下文（M5）

`workflow_next` 除了积木说明，还给出：
- 学习目标和时间预算（来自项目）；
- 当前单元（如果在循环里）；
- 当前单元相关节点的状态摘要（来自 `progress()` 的 `AttentionReason`）。

积木说明可以据此决定"已掌握就跳过直觉部分"，但这个判断写在积木里，不在引擎里。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 通用工作流图（DAG） | 用户写不出来；编排器和组装器的成本远超现有需求 |
| 引擎内置"掌握"标准，比如正确率 ≥ 80% | 不同活动的"完成"含义不同（见背景），会把一种教学观写死在基础设施里 |
| 把单元等同于知识图谱里的概念节点 | 项目里程碑、研究问题、论证都不是概念节点 |
| 只靠 agent 编排，不加循环 | 决策不可见、不可比较，场景 A、B 的主线需要可预期 |

## 兼容

新增字段（`repeat`、`until`、`max`、`otherwise`、`produces`）都是可选的；没有它们的工作流行为不变。格式版本号加 1；旧运行的快照不含 `units`，按无循环处理。

## 待讨论

1. `otherwise: ask` 时，"等待决定"由谁来回应：只有学习者（网页），还是 agent 也可以？
2. 学习者在循环中途改了单元列表，正在执行的单元怎么处理（建议：做完当前一步再生效）。
3. `until` 是否需要读"本单元内某一步被重试了几次"（`attempts(recall)`）。
4. 单元的状态和评价要不要写回 Episteme（建议：不写，单元属于一次学习的议程，不是理解）。
